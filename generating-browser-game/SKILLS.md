# Browser Quest Game Generator

## Instructions

1. **Analyze the Quest Input**: Identify the quest's narrative hook, mission steps, twist/choice, and rewards. If the user provides a quest generated by the quest generator skill, extract those elements directly. If no quest is provided, ask the user to supply one or generate a default quest with a retrieval objective and a moral-choice twist.
2. **Define the Game Structure**: The game MUST follow a linear sequence of exactly 5 screens rendered on a single HTML5 `<canvas>`:
   - **Screen 1 — Title & Objective**: The quest name as a heading, the narrative hook as flavour text, and a 1-sentence objective telling the player what they must accomplish. Ends with a "Tap or Click to Begin" prompt.
   - **Screen 2 — Mission Steps (Playable Challenge)**: Each mission step from the quest becomes an interactive challenge. Present steps one at a time. Each step MUST require at least one player action (e.g., tap a target, choose a direction, drag to dodge, click to search). Display a progress indicator showing "Step X of Y".
   - **Screen 3 — The Twist (Choice Screen)**: Present the quest's twist as a branching choice with exactly 2 clearly labeled options. Each option MUST be a tappable/clickable button at least 48×48 CSS pixels. The player's choice MUST visibly affect the outcome shown on the ending screen.
   - **Screen 4 — Outcome & Rewards**: Show the consequence of the player's choice in exactly 2 sentences. Display the rewards earned based on their choice path. Include a final score based on performance during the mission steps (e.g., speed, accuracy, items collected).
   - **Screen 5 — Game Over & Restart**: Display "Quest Complete" as a heading, the player's final score, and a clearly labeled "Restart" button. Pressing restart MUST reset all game state and return to Screen 1.
3. **Implement as a Single HTML File**: All CSS MUST be in a `<style>` block in the `<head>`. All JavaScript MUST be in a single `<script>` block before the closing `</body>` tag. The game MUST render entirely on an HTML5 `<canvas>` element with the exception of the restart button, which MAY be a styled `<button>` element.
4. **Implement Input Controls**:
   - **Desktop**: The game MUST respond to `click` events for all choices, actions, and navigation. If a challenge step involves movement, respond to `mousemove` as well.
   - **Mobile**: The game MUST respond to `touchstart` and `touchend` events for all choices, actions, and navigation. If a challenge step involves movement, respond to `touchmove` as well.
   - Both mouse and touch listeners MUST be registered unconditionally. Do NOT use `user-agent` sniffing to choose one input path.
   - All interactive targets (buttons, choice options, tap zones) MUST be at least 48×48 CSS pixels.
5. **Implement Scoring**: Award points during mission steps based on player performance (e.g., +100 for completing a step quickly, +50 for accuracy). The score MUST be visible during gameplay and displayed on the outcome screen.
6. **Apply Visual Style**: Use a consistent color palette of no more than 5 colors. Draw all game elements using canvas primitives (rectangles, circles, lines) or emoji characters. Use a single sans-serif font family for all text. Narrative text MUST be word-wrapped to fit within the canvas width with at least 16px horizontal padding on each side.
7. **Game Loop**: Use `requestAnimationFrame` for all rendering. Do NOT use `setInterval` or `setTimeout` for the main render loop.

## Constraints

- Do NOT split the game across multiple files. The entire game MUST be a single `.html` file.
- Do NOT use any external libraries, frameworks, CDNs, or dependencies (e.g., no Phaser, no p5.js, no jQuery, no Google Fonts links).
- Do NOT use `setInterval` or `setTimeout` for the main game loop; use `requestAnimationFrame` exclusively.
- Do NOT use image assets, audio files, or any resource that requires a network request or a separate file.
- Do NOT use `user-agent` sniffing or `navigator.platform` to detect input method; register both mouse and touch listeners unconditionally.
- Do NOT create interactive targets (buttons, choices, tap zones) smaller than 48×48 CSS pixels.
- Do NOT skip any of the 5 screens; every screen must be reachable during normal play.
- Do NOT auto-advance past the title screen; the player must tap or click to begin.
- Do NOT skip the twist/choice screen; the player MUST make a choice that affects the outcome.
- Do NOT show the same outcome text regardless of the player's choice; each path MUST produce a visibly different result and reward set.
- Do NOT omit the `<meta name="viewport">` tag; the game MUST be responsive on mobile viewports.
- Do NOT use `alert()`, `prompt()`, or `confirm()` for any game interaction.
- Do NOT make mission steps passive (text-only with a "Next" button); every step MUST require a meaningful player action beyond just clicking "Continue".
- Do NOT use more than 5 colors in the game's visual palette.
- Do NOT render text that overflows the canvas horizontally; all narrative text MUST be word-wrapped.
- Do NOT add sections, fields, or formatting to the output that are not specified in the Output Format template above.
